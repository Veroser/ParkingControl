# ParkingControl — требования к информационной системе

## 1. Назначение системы

ParkingControl — настольная информационная система для автоматизации работы
платной парковки ограниченного масштаба (одна парковочная площадка с
несколькими зонами). Система предназначена для учёта клиентов, их
автомобилей, парковочных мест и тарифов, а также для регистрации въезда и
выезда автомобилей с расчётом стоимости стоянки.

Система не является биллинговой, не взаимодействует с платёжными системами,
не управляет шлагбаумами и камерами. Это учётное приложение для оператора
парковки.

## 2. Пользователи и роли

Система рассчитана на одного пользователя — **оператора парковки**. Роли и
разграничение прав доступа в рамках проекта не реализуются (см. раздел 8
«Границы проекта»).

Оператор выполняет все действия: ведёт справочники, регистрирует въезды и
выезды, формирует отчёты.

## 3. Основные пользовательские сценарии

### Сценарий 1. Регистрация нового клиента
Оператор открывает раздел «Клиенты», нажимает «Добавить», вводит ФИО,
телефон и (необязательно) email, сохраняет запись. Система проверяет
обязательность полей и уникальность телефона.

### Сценарий 2. Добавление автомобиля клиенту
Оператор открывает раздел «Автомобили», выбирает клиента, вводит госномер
и модель, сохраняет. Система проверяет формат госномера и уникальность
госномера.

### Сценарий 3. Открытие парковочной сессии (въезд)
Оператор открывает раздел «Сессии», выбирает автомобиль, свободное место
и тариф, нажимает «Открыть сессию». Система в одной транзакции проверяет,
что место свободно и у автомобиля нет активной сессии, после чего создаёт
запись о въезде.

### Сценарий 4. Закрытие парковочной сессии (выезд)
Оператор выбирает активную сессию, нажимает «Закрыть сессию»,
подтверждает операцию. Система рассчитывает стоимость по тарифу и
времени стоянки, фиксирует время выезда и итоговую сумму.

### Сценарий 5. Поиск клиента или автомобиля
Оператор вводит часть ФИО, телефона, госномера или модели в поле поиска.
Система отображает совпадения. При отсутствии результатов выводится
сообщение «Ничего не найдено».

### Сценарий 6. Просмотр отчёта по выручке
Оператор открывает раздел «Отчёт», задаёт период, получает таблицу с
выручкой, количеством сессий и средней длительностью стоянки по зонам.

### Сценарий 7. Удаление клиента или автомобиля
Оператор выбирает запись и нажимает «Удалить», подтверждает операцию.
Система удаляет запись, если это не нарушает ссылочную целостность
(нельзя удалить клиента, у которого есть автомобили или сессии).

## 4. Функциональные требования

Формулировки проверяемые: каждое требование можно продемонстрировать.

| ID | Требование |
|----|------------|
| FR-01 | Система позволяет просматривать, добавлять, изменять и удалять клиентов (ФИО, телефон, email). |
| FR-02 | Система позволяет просматривать, добавлять, изменять и удалять автомобили (госномер, модель, владелец). |
| FR-03 | Система отображает список свободных парковочных мест с указанием зоны и номера места. |
| FR-04 | Система позволяет открыть парковочную сессию: выбрать автомобиль, свободное место и тариф. |
| FR-05 | Система позволяет закрыть активную парковочную сессию с расчётом стоимости. |
| FR-06 | Система выполняет поиск клиентов по ФИО или телефону и автомобилей по госномеру или модели. |
| FR-07 | Система выполняет поиск сессий по госномеру или номеру места, а также фильтрацию «только активные». |
| FR-08 | Система формирует отчёт по выручке, количеству сессий и средней длительности стоянки по зонам за выбранный период. |
| FR-09 | Система проверяет обязательность полей и корректность форматов (телефон, госномер) перед сохранением. |
| FR-10 | Система запрашивает подтверждение перед удалением записей и закрытием сессии. |
| FR-11 | Система выводит информативные сообщения об успехе и об ошибках, не раскрывая строку подключения и пароли. |
| FR-12 | Система при отсутствии результатов поиска выводит сообщение «Ничего не найдено». |

## 5. Бизнес-правила

### BR-1. Уникальность телефона клиента
Телефон клиента уникален. При попытке сохранить клиента с уже
существующим телефоном система отклоняет операцию и выводит сообщение
«Клиент с таким телефоном уже существует». Правило реализовано на двух
уровнях: проверка в `ParkingService.SaveClient` (понятное сообщение) и
ограничение `UNIQUE` на столбце `Clients.Phone` (защита на уровне БД).

### BR-2. Один автомобиль — одна активная сессия; одно место — одна активная сессия
Автомобиль не может одновременно находиться на двух местах, а место не
может быть занято двумя автомобилями. Правило реализовано через:
- фильтрованные уникальные индексы `UX_Sessions_ActiveSpace` и
  `UX_Sessions_ActiveVehicle` (где `ExitTime IS NULL`);
- проверку в транзакции `OpenSessionWithLock` с `UPDLOCK, HOLDLOCK`.

### BR-3. Время выезда позже времени въезда
Ограничение `CK_Sessions_Times` на таблице `ParkingSessions` не позволяет
зафиксировать выезд раньше въезда.

## 6. Транзакционная операция

### Открытие парковочной сессии
Операция затрагивает таблицу `ParkingSessions` и логически связана с
проверками по `ParkingSpaces` и `ParkingSessions`. Выполняется в одной
транзакции с уровнем изоляции `Serializable`:

1. `BEGIN TRANSACTION`.
2. Проверка: `SELECT COUNT(*) FROM ParkingSessions WITH (UPDLOCK, HOLDLOCK)
   WHERE SpaceId = @SpaceId AND ExitTime IS NULL`. Если больше нуля —
   исключение «Место уже занято», откат.
3. Проверка: `SELECT COUNT(*) FROM ParkingSessions WITH (UPDLOCK, HOLDLOCK)
   WHERE VehicleId = @VehicleId AND ExitTime IS NULL`. Если больше нуля —
   исключение «У автомобиля уже есть активная сессия», откат.
4. `INSERT INTO ParkingSessions (...) OUTPUT INSERTED.SessionId`.
5. `COMMIT`.

При любом исключении выполняется `ROLLBACK`. Проверка и запись выполняются
согласованно, что исключает гонку между двумя операторами (требование 3.6
методических указаний).

### Закрытие парковочной сессии
Аналогично выполняется в транзакции `Serializable`: чтение активной сессии
с `UPDLOCK, HOLDLOCK`, расчёт стоимости, `UPDATE` полей `ExitTime` и
`TotalCost`, `COMMIT`. При ошибке — `ROLLBACK`.

## 7. Сущности и ограничения

| Сущность | Назначение | Ключи и ограничения |
|----------|------------|---------------------|
| `ParkingZones` | Зоны парковки | PK `ZoneId`; `UNIQUE(Name)`; `CHECK(Capacity > 0)` |
| `ParkingSpaces` | Парковочные места | PK `SpaceId`; FK `ZoneId → ParkingZones`; `UNIQUE(ZoneId, SpaceNumber)` |
| `Tariffs` | Тарифы | PK `TariffId`; `UNIQUE(Name)`; `CHECK(PricePerHour > 0)` |
| `Clients` | Клиенты | PK `ClientId`; `UNIQUE(Phone)`; `NOT NULL` на `FullName`, `Phone` |
| `Vehicles` | Автомобили | PK `VehicleId`; FK `ClientId → Clients`; `UNIQUE(PlateNumber)` |
| `ParkingSessions` | Сессии стоянки | PK `SessionId`; FK на `Vehicles`, `ParkingSpaces`, `Tariffs`; `CHECK(ExitTime > EntryTime)`; фильтрованные `UNIQUE`-индексы на активные сессии |

Связи: `ParkingZones 1—N ParkingSpaces`, `ParkingSpaces 1—N ParkingSessions`,
`Clients 1—N Vehicles`, `Vehicles 1—N ParkingSessions`,
`Tariffs 1—N ParkingSessions`. Отношений «многие ко многим» в предметной
области нет — таблица связи не требуется.

## 8. Границы проекта (что не реализуется)

- Нет авторизации и разграничения ролей — один оператор.
- Нет интеграции с платёжными системами, эквайрингом, фискализацией.
- Нет управления шлагбаумами, камерами, RFID-метками.
- Нет мобильного клиента и веб-интерфейса.
- Нет REST API и микросервисной архитектуры.
- Нет бронирования мест заранее — только фактический въезд.
- Нет абонементов, скидок, льгот.
- Нет экспорта отчётов в Excel/PDF — только отображение в таблице.
- Нет уведомлений (email/SMS) клиентам.
- Нет журналирования действий пользователя и аудита.

Перечисленные функции не входят в обязательную часть и не влияют на
оценку; их absence зафиксировано сознательно, чтобы не расширять объём
работы за пределы требований методических указаний.
